# VeriFit 프로젝트 경험 정리

> 한 줄 소개: 적금의 광고 최고금리 대신, 사용자가 실제로 충족할 수 있다고 입력한 조건을 기준으로 예상 적용금리와 세후 이자를 계산하고 그 근거를 보여주는 서비스.

이 문서는 포트폴리오·발표·면접에서 프로젝트의 문제 정의부터 구현까지 설명하기 위한 기록이다. **구현한 사실**, **설계 가설**, **아직 검증하지 못한 부분**을 구분한다.

## 1. 출발점: 어떤 문제를 풀려고 했나

적금 비교 화면에서 눈에 띄는 숫자는 대개 `최고금리`다. 하지만 최고금리는 급여이체, 카드 실적, 첫 거래, 자동이체 등 여러 우대를 모두 충족해야 가능한 값일 수 있다. 상품마다 조건의 종류·기준 금액·유지 기간·중복 적용 규칙도 달라서, 사용자가 공시 문장을 일일이 읽고 자신의 상황에 맞게 계산하기 어렵다.

기존의 “최고금리순 정렬”에서 빠진 질문은 다음과 같다.

- **내가 할 수 있는 조건만 적용하면 금리가 얼마인가?**
- **그 금리로 매월 일정액을 넣으면 세후 이자가 얼마인가?**
- **왜 그 금리가 나왔는지, 원문에서 확인할 수 있는가?**
- **월 납입액이나 가능한 우대조건을 바꾸면 결과가 어떻게 달라지는가?**

문제 정의는 실제 사용자 인터뷰로 검증된 결론이 아니라, 적금 공시 구조와 비교 과정을 관찰해 세운 **제품 가설**이다. 그래서 서비스는 “이 상품에 가입하라”는 추천보다 “입력한 조건에서의 계산과 근거를 확인한다”는 범위로 잡았다.

## 2. 가설적 페르소나와 사용 장면

**페르소나 — 적금을 비교하는 직장인**: 매달 30만~50만 원을 1~2년 저축하려 한다. 급여이체는 가능하지만 특정 카드의 월 사용액을 새로 맞출 생각은 없다. 금융상품 설명을 읽을 수는 있지만 여러 상품의 우대조건을 수작업으로 계산할 시간은 없다. 이 인물은 설계용 가상 페르소나이며, 실제 조사 참여자가 아니다.

사용 흐름은 다음처럼 설정했다.

1. 사용자가 “월 30만 원씩 1년, 급여이체 가능, 카드는 안 써”처럼 자신의 상황을 말한다.
2. 서비스가 이해한 납입액·기간·금융 습관을 먼저 보여준다.
3. 상품별 기본금리, 충족한 우대, 예상 적용금리, 일반과세 기준 세후 이자를 비교한다.
4. 관심 상품의 우대조건과 공시 원문 인용을 확인한다.
5. “월 50만 원으로 바꿔줘”처럼 조건을 바꿔 다시 계산한다.

핵심 UX 판단은 **자연어로 시작하되 결과는 검산 가능한 구조화 데이터로 보여주는 것**이다. 긴 AI 답변이 상품 카드를 중복하거나 덮지 않도록, 결과 화면에서는 비교 카드를 중심에 두고 자연어 설명은 접어 둔다.

## 3. 데이터 확보와 범위 설정

출처는 금융감독원 **금융상품 한눈에 적금 상품 API**(`savingProductsSearch.json`)다. 현재 배치 기본 권역은 `topFinGrpNo=020000`(은행권)이다. API의 상품 기본 정보와 기간별 금리 옵션을 페이지 끝까지 수집한다.

| 원천 데이터 | 서비스에서의 역할 |
| --- | --- |
| 금융회사·상품명·공시월·가입 대상·가입 방법 | 상품 식별과 표시, 가입 조건 추출 입력 |
| 적립 방식·기간·기본금리·최고금리·단리/복리 | 계산을 위한 확정 기준값 |
| 우대조건 자유 텍스트 | LLM 구조화 대상 및 원문 근거 |

수집 단계에서 금리를 부동소수점 퍼센트가 아닌 **bps 정수**로 바꾼다(3.60% → 360bp). API 코드의 의미도 실측에 맞춰 매핑한다. 예를 들어 `rsrv_type`의 `F`는 자유적립식, `S`는 정액적립식이고, 별도 필드인 `intr_rate_type`의 `S`는 단리다. 같은 문자라도 필드에 따라 뜻이 달라 분리해서 처리했다.

상품별 우대조건은 정형 컬럼 하나로 끝나지 않는다. “월 50만 원 이상을 6개월 유지”, “A와 B 중 하나”, “두 우대 중복 불가”, “합계 최대 0.9%p”처럼 서로 다른 규칙이 한 문장에 섞여 있다. 그래서 원문 전체를 검색만 하는 대신, **계산 가능한 관계로 구조화**하는 단계를 만들었다.

## 4. 두 종류의 그래프: 지식 구조와 처리 흐름

### 4-1. 상품 Knowledge Graph

별도 그래프 DB를 도입한 것이 아니라, 관계를 **Pydantic 모델과 SQLite 테이블/참조**로 표현했다.

```text
Institution ──offers──> Product ──has──> RateOption
                           │                  │
                           │                  └── BonusGroup ──contains──> Bonus
                           │                                            ├── requires──> Requirement
                           └── eligibility──> Requirement             └── supported_by──> Evidence
```

- `RateOption`: 기간·적립 방식·단리/복리·기본/최고금리.
- `BonusGroup`: 우대금리 합산 한도와 중복 불가 쌍.
- `Bonus`: 개별 우대폭과 `AND`/`OR`/단일 조건 관계.
- `Requirement`: 급여이체·카드실적 등 **19개 표준 코드**와 금액·기간·횟수·채널 같은 매개변수. 분류할 수 없는 조건은 `other`.
- `Evidence`: 해당 우대나 가입 자격을 추출한 원문 인용과 출처 필드.

예를 들어 “월 50만 원 이상 급여이체를 6개월 이상 유지하면 연 1.0%p”는 `Bonus(rate_bps=100)`가 `salary_transfer` 조건과 `min_amount_won=500000`, `min_months=6`을 참조하고, 원문 인용을 `Evidence`로 가지는 형태가 된다. 조회 결과에서 근거를 보여줄 때는 벡터 검색으로 비슷한 문장을 찾지 않고 **실제로 계산에 사용한 Bonus의 Evidence**를 따라간다.

### 4-2. LangGraph 워크플로

위의 지식 그래프와 별개로, LangGraph는 LLM 호출·검증·재시도·종료를 제어한다. **오프라인 상품 구축 그래프**와 **온라인 사용자 응답 그래프**를 나눴다. 비싼 상품 문장 해석을 요청마다 반복하지 않고, 검증된 구조를 미리 저장하기 위한 분리다.

## 5. 오프라인: 공시 문장을 계산 가능한 데이터로 만들기

```text
금감원 API 수집 → 적립 방식/기간별 정규화
→ Extractor LLM 3회 실행·일치도 병합
→ 코드 검증 → Reviewer LLM 검토
→ 필요 시 상품당 1회 재추출
→ 기간별 accept/exclude → SQLite 저장·로그
```

Extractor에는 상품의 우대조건 원문과 API에서 확정된 금리 옵션을 준다. LLM은 우대 항목·표준 조건 코드·세부 기준·합산 한도·중복 불가 관계·원문 인용을 추출한다. 같은 추출을 3회 수행하고 우대의 조건 코드뿐 아니라 **우대폭과 금액·기간 기준까지** 대조한다. 서로 다르게 나온 항목은 `other`로 낮춰 무리하게 적용하지 않는다. 이는 같은 모델의 반복 결과를 비교하는 것이지, 독립 모델 간 합의나 정답 검증은 아니다.

코드 검증은 인용문이 실제 원문에 있는지 확인하고, **이해한 우대를 모두 적용할 수 있는 최대 금리**가 `공시 최고금리 − 기본금리`와 일치하는지 검사한다. 합계가 모자라면 누락을, 넘으면 그룹 한도나 중복 불가 규칙의 누락을 의심한다. Reviewer는 의미상의 문제를 다시 지적한다. 통과하지 못한 기간 옵션은 저장에서 제외하고 이유를 `extraction_log`에 남긴다. 한 상품의 자유적립식·정액적립식 결과는 합친 뒤 한 번에 저장해, 나중 저장이 앞선 옵션을 덮어쓰지 않게 했다.

검증 범위를 과장하지 않기 위해 구분할 점도 있다. **현재 코드에서는 Reviewer 호출 자체가 실패해도 코드 검증을 통과한 옵션을 `reviewer_unavailable`로 표시하고 저장할 수 있다.** 따라서 “저장된 모든 옵션이 두 검증을 모두 통과했다”라고 주장하면 안 된다.

## 6. 온라인: 자연어 입력부터 답변 검증까지

```text
React UI → POST /api/v1/ask
→ Analyzer LLM: 문장 → UserProfile
→ 입력 검증: 금액·기간·조건의 원문 대조
→ SQLite 상품 조회 + 조건 매칭 + 이자 계산
→ Writer LLM: 계산값을 설명문으로 변환
→ 코드 검증: 상품 키·금리·세후 이자·근거 인용 대조
→ Reviewer LLM: 과장·논리 비약 검토
→ 통과 시 응답 / 재작성 1회 / 정형 답변 fallback
```

Analyzer가 뽑은 월 납입액과 기간은 인용 문구가 실제 사용자 입력에 있는지, 인용된 숫자와 구조화된 값이 일치하는지 **코드로 다시 확인**한다. 필수값이 없으면 `needs_input`으로 질문한다. `thread_id`와 메모리 checkpointer로 이전 대화에 이어 조건을 수정할 수 있다.

상품 판정과 계산에는 LLM을 쓰지 않는다. 사용자가 입력하지 않은 사실은 충족하지 않은 것으로 보수적으로 처리하고, 기간이 정확히 일치하는 옵션에 대해 우대조건의 `AND`/`OR`, 중복 불가, 그룹 한도를 적용한다. 금리는 최고금리를 넘지 않도록 제한한다. 이자 계산은 `Decimal`로 단리/월복리를 구분하고, **매월 초 납입·일반과세 15.4%** 가정 아래 원 단위 반올림한다.

Writer의 문장과 별개로 API는 상품별 구조화 계산 결과를 반환한다. Writer가 함께 제출한 **구조화된 상품 주장**의 상품 키·금리·세후 이자·인용을 계산 결과와 대조하고, Reviewer 지적이 있으면 한 번 재작성한다. 재검증 실패나 LLM 장애 시에는 검증되지 않은 문장을 내보내는 대신 **코드가 만든 정형 답변**을 사용한다. `POST /api/v1/evaluate`는 구조화된 `UserProfile`을 바로 받아 LLM 없이 같은 계산 엔진을 호출하는 경로다.

## 7. 웹 화면에 반영한 결과

React/TypeScript 웹에서 자연어 입력, 예시 문장, 인식한 조건 칩, 상품별 금리 비교 바, 적용·미적용 우대, 세후 이자·만기 예상액, 공시 근거 drawer, 후속 대화, 정렬, 라이트/다크 테마를 제공한다. 결과의 중심은 **상품 카드와 숫자**다. 자연어 분석문은 접을 수 있는 보조 정보로 두어 같은 상품 정보가 두 번 크게 노출되지 않게 했다. 카드에는 실제 가입 조건과 공시를 확인해야 한다는 안내도 함께 둔다.

## 8. 구현 과정에서 내린 주요 결정과 배운 점

| 판단 | 이유와 배운 점 |
| --- | --- |
| 최고금리 정렬보다 개인 조건별 계산 | 최고금리는 사용자에게 실제 적용될 금리가 아니므로, 우대 충족 여부를 드러내야 비교가 의미 있다. |
| LLM 해석과 코드 계산 분리 | LLM이 숫자를 자유롭게 만들지 않게 하고, 동일 입력에 대한 계산을 재현 가능하게 했다. |
| 원문 인용을 그래프 관계로 보관 | 결과의 이유를 실제 계산 경로에서 바로 추적할 수 있다. |
| `other`와 기간별 제외 | 해석하기 어려운 조건을 억지로 적용하지 않고, 유효한 기간 옵션까지 함께 버리지 않는다. |
| 반복 추출 + 도달가능성 검사 | 추출이 흔들리는 경우와 산술적으로 모순되는 경우를 서로 다른 방식으로 잡는다. 반복 합의만으로 정답이 보장되지는 않는다. |
| SQLite부터 사용 | 현재 규모에서는 관계형 참조로 필요한 그래프 탐색이 가능해 별도 그래프 DB를 도입하지 않았다. |
| 온라인 정형 fallback | 설명 생성이 실패해도 검증된 계산값과 미검증 문장을 섞어 보여주지 않는다. |

실제로 겪은 구현 문제도 설계에 반영했다. API의 적립 방식 코드와 단리/복리 코드를 혼동하지 않도록 분리했고, 적립 방식별 저장이 다른 옵션을 덮어쓰는 문제를 상품 단위 병합 저장으로 해결했다. 우대의 일부 조합이 최고금리에 도달한다고 통과시키면 **동시 적용 가능한 전체 합계가 최고금리를 초과할 수 있는** 문제를 발견해, 최대 도달 가능 합계를 비교하도록 검증 기준을 강화했다.

## 9. 현재 상태와 표현할 때의 경계

- 백엔드 API, 두 LangGraph 흐름, SQLite 저장·조회, 계산기, React UI와 자동 테스트가 코드에 있다. 데이터 구축은 배치가 별도 실행되어야 한다.
- 2026-09-26 로컬 개발 DB 확인 시 `products` 6개, `rate_options` 24개, `bonuses` 44개가 있었다. 이는 **부분 배치의 로컬 스냅샷**이지 전체 공시 상품 커버리지나 품질 지표가 아니다. DB 파일은 Git에 포함하지 않는다.
- 실제 사용자 인터뷰·사용성 실험이나 사람이 만든 정답셋으로 정확도를 측정하지 않았다. 페르소나는 가설이며, 반복 추출·코드 검증·LLM Reviewer를 “정답률 보증”이라고 표현하지 않는다.
- 온라인 코드 검증은 Writer의 구조화된 상품 주장을 대조한다. 자유 서술 문장의 모든 숫자·해석을 독립적으로 파싱해 검증하는 것은 아니므로 Reviewer와 정형 fallback이 있어도 무오류를 보증할 수 없다.
- 현재 온라인 매칭은 **기간 일치와 우대조건 판정**이 중심이다. 저장된 가입 자격을 모두 자동 필터링하지 않으므로 결과를 “가입 가능 상품”이라고 단정하지 않는다. 공시와 실제 적용 여부는 금융회사에서 확인해야 한다.
- 이자 계산은 매월 초 납입과 일반과세 기준의 예상치이며, 비과세 특례·실제 납입일·가입 시점의 금리 변경 등은 반영하지 않는다.
- checkpointer는 `MemorySaver`이므로 서버 재시작 후 대화 상태가 영속 보존되는 구조는 아니다.

## 10. 발표·면접용 짧은 설명

“적금 비교에서 최고금리만 보면 사용자가 실제로 받을 금리를 알기 어렵다는 문제에서 출발했습니다. 금융감독원 공시의 자연어 우대조건을 LLM으로 추출해 상품·기간·우대·표준 조건·원문 근거의 관계로 SQLite에 저장했습니다. 추출 결과는 근거 문장과 최고금리 도달 가능성을 코드로 검사하고, 실시간 요청에서는 AI가 사용자 말을 구조화하되 우대 판정과 세후 이자 계산은 결정론적 코드가 맡도록 분리했습니다. 마지막으로 AI 설명의 숫자와 근거를 계산 결과에 다시 대조하고, 실패하면 정형 답변으로 전환합니다. 현재는 개인 조건별 비교가 가능한 프로토타입이며, 사용자 검증과 데이터 커버리지·정확도 평가는 후속 과제입니다.”
